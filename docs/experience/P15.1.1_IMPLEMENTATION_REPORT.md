## Architecture Implemented

### Core Flow

```
REQUEST
   ↓
ProductResolver (hostname → product context)
   ↓
EcosystemResolver (country/region/destination)
   ↓
ConfigurationLoader (merge hierarchy)
   ↓
ExperienceLoader (experience type)
   ↓
ModuleResolver (enabled modules)
   ↓
CapabilityResolver (required capabilities)
   ↓
ExperienceComposer (theme/branding/navigation/SEO/i18n)
   ↓
EXPERIENCE CONTEXT
```

### Key Design Decisions

1. **Resolver Pattern**: Separated concerns (product, ecosystem, module, capability) for testability
2. **Immutable Context**: ExperienceContext is immutable after resolution
3. **Configuration Inheritance**: Deep merge with union arrays
4. **No Hardcoded Values**: All product/destination data from configuration
5. **Event-Driven**: Lifecycle events for observability

## Experience Engine Boundaries

### Can Access

- Product/Destination configuration
- Module/Capability registries
- Configuration hierarchy
- Platform interfaces via contracts

### Cannot Access

- Direct PostgreSQL queries
- Direct storage provider SDKs
- Direct media processing libraries
- Business Aggregate entities
- API Layer directly
- Repository Engine internals

## Resolution Flow

### Product Resolution (5 strategies)

1. Subdomain: `albasie.valdi.app` → company=albasie
2. Hostname: `valdi.app` → destination=valdi
3. Path: `/cl/los-rios/valdi` → country=cl, region=los-rios, destination=valdi
4. Query: `?ecosystem=cl-los-rios-valdi`
5. Header: `X-Ecosystem: cl-los-rios-valdi`

```

    ↓

    ↓

    ↓

    ↓

```
